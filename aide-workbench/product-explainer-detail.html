核心变化：围绕什么组织工作？

Mino 通用 Agent 也能产出文件、调用工具并与人协作。这里比较数据开发中的常见使用路径。

B

一条需求怎样走到交付？

以“每天 09:00 前交付渠道交易日报”为例。一线业务先明确统计口径与验收条件，Aide 再把它拆成可追踪的节点。订单明细、退款处理和调度配置可并行推进；日报依赖订单与退款成果，测试依赖日报与调度成果。

节点显示当前成果和下一步。当前动作可能是确认退款日期口径、接手转交、评审版本，或修复测试失败。发布前需通过测试并取得明确授权。模拟首跑通过后，演示需求才标记为交付。这样能分别看清产物与交付状态。交付成功后，再把这次需求的决定和证据装订成一版交付说明书。

C

节点接过什么，又交出什么？

每个节点保留输入、产物、版本、负责人、待确认事项与证据。负责人确认当前版本后，下游才接收有效成果。讨论可以提出修改，但一条普通消息不等于确认、评审通过或发布授权。

同一需求的上下文持续传递，节点工作区随阶段改变：

阶段 工作区聚焦内容
需求理解 统计口径和待确认事项
数据开发 SQL、字段与结果预览
数据测试 检查项和失败证据
发布上线 发布包、授权与首跑验收

成员在对应工作区处理当前任务，而不是在同一聊天页不断追加消息。

节点信息 渠道日报开发中的例子 用途
输入 已确认的订单明细与退款处理版本 知道指标来自哪份上游成果
输出 日报 SQL、字段和预览 留下可检查的候选产物
Owner 与决策 数据开发 审阅金额口径并确认版本 明确谁对结果负责
证据 版本差异、讨论、评审、测试结果 支持下游使用与回溯

若金额空值规则改变，节点产生 V2。依赖旧版本的下游成果、旧确认与旧评审需要重新核对，测试也要重跑。流程本身也能调整：例如新增“日期 × 渠道唯一性检查”，使它成为发布前的必需测试。新增检查会形成新的流程版本，并让测试与发布包重新核验。

交付说明书以需求或场景为归档单元。它记录业务目标、指标口径、来源与目标表、任务节点、SQL 版本和依赖。它也保存评审、测试、发布证据、历史决定和负责人。

ads_channel_trade_di 与 channel_trade_daily 是跨需求匹配线索。新需求进入时，Agent 可从标题和描述识别这些线索，再找回对应交付版本；结论仍以原交付版本为引用对象。

E

一个具体变更：金额空值怎么处理？

以 数据分析 提出的“金额为空时按 0 处理”为例，变更沿同一需求流转：

  1. 提出规则：数据分析 在日报节点说明空值口径及其影响。
  2. 形成 V2：Agent 给出候选；数据开发 检查 SQL 与字段，应用修改。
  3. 评审与确认：若发起评审，评审人须全部通过 V2；再由负责人确认。旧评审不能顺延。
  4. 下游重测：重新运行数据测试，并确认当前版本报告。
  5. 发布验收：准备发布包；经明确授权后模拟发布，用首跑证据验收。

公开原型用切换演示成员来走通各角色操作，展示讨论、修改、确认、评审和重测的状态变化；它还不是在线多人同时登录协作。

交付之后也能继续演进。在产品目标动线中，Aide 先关联一个飞书项目（Meego）空间和项目，再定时检查新工作项；发现后进入首页待办，交给负责人确认。已有工作项仍可手动选择进入。

虚构需求“渠道日报增加店铺维度”进入时，Agent 读取标题与描述。它识别 ads_channel_trade_di 和每日任务 channel_trade_daily，自动召回相关的交付第 1 版。发起人不必先手动寻找说明书。

新需求工作区分开标明两种来源：本次需求来自飞书项目工作项；旧粒度、退款日期口径、明细来源、日报 SQL 与旧证据来自原交付版本及其节点。若线索不足或命中多个版本，工作区显示“未找到”或“待选择”，不把猜测当成已确认规则。

店铺字段来源与退款如何关联店铺属于新规则，需由相关人员确认。随后 Agent 生成候选，数据开发 检查 SQL、字段、依赖和测试影响；按需评审当前候选，由 Owner 确认后重测，再经明确授权发布。交付成功才追加新说明书版本。原版本保留，原评审与测试不能自动证明修改后的 SQL。

三类角色的工作重心如何变化？

角色 常见路径中的负担 在需求节点中的主要动作
一线业务 反复询问结果是否满足目标 确认目标、关键口径和交付验收
数据分析 把规则发给 数据开发，再等转述后的结果 在相关节点提出规则，审阅指标和当前版本
数据开发 收集上下文、复制结果、转述反馈 审核工程方案与产物，处理测试、评审和发布

这不是把责任交给 Agent。业务规则由相关人员确认，产物质量由 Owner 把关，评审和发布有独立动作。角色共享上下文，责任仍有明确归属。

读者可以怎样看 Demo？

打开公开演示：Aide 数据工作台，沿下面六站体验产品动线。示例数据均为虚构。

  1. 需求总览：看我的待办、受阻需求与下一步；试着切换成员和个性化首页。
  2. 节点上下文：进入“渠道交易日报建设”，查看依赖图、上游输入和当前产物。
  3. 转交与评审：在节点发起转交或对当前版本评审，再切换成员接手或提交结论。
  4. 版本与测试：提出金额空值修改并形成 V2；按需完成当前版本评审，由负责人确认后查看重测证据。
  5. 发布与验收：审阅发布包，明确授权模拟发布，再看首跑结果和交付记录。
  6. 交付后变更：查看定时发现的示意飞书项目需求，也可手动选择已有工作项；再看召回结果，确认新规则和证据。
